================================================================================
DOMAIN 5: REUSABILITY ASSESSMENT — PRESENTON BACKEND FOR SHOTHIK/HERMES
================================================================================
Separating directly reusable backend code/assets from concepts that should
only inspire our custom Hermes implementation.

Context:
  - Shothik has a Next.js frontend (keep unchanged).
  - Hermes is the backend orchestrator.
  - Workspace: C:\Users\USER\hermes\shothik-web-mirror-v2
  - Shothik uses InsForge (Postgres-based BaaS) for DB/auth/storage.
  - Presenton license: Apache 2.0 (compatible with reuse).

2.1 LLM Provider Abstraction (llm_config.py + llm_provider.py + constants/llm.py)
--------------------------------------------------------------------------------
Files:
  - servers/fastapi/utils/llm_config.py (400+ lines)
  - servers/fastapi/utils/llm_provider.py (200+ lines)
  - servers/fastapi/constants/llm.py
Assessment:
  The pattern of a single get_llm_config() -> ClientConfig + get_model() ->
  model_name is sound. The 16-provider support is comprehensive.
  HOWEVER: the implementation depends on llmai (an external wrapper library).
  This is a hard dependency that Hermes should NOT adopt.
What to keep:
  - The LLMProvider enum (16 providers)
  - The ClientConfig pattern (one config class per provider)
  - The env-based configuration approach
  - The provider detection predicates
What to rewrite:
  - Replace llmai with direct provider SDK calls (openai, anthropic, google-genai)
  - OR: use Hermes' existing provider routing (Hermes already supports
    OpenRouter, Anthropic, OpenAI, etc.)
  - Strip Codex OAuth flow (ChatGPT-specific, not needed for Hermes)
  - Strip ChatGPTClientConfig (presenton-specific)
Effort: HIGH — every LLM call site changes when the underlying library changes.

TIER 3: INSPIRATION ONLY — CUSTOM HERMES IMPLEMENTATION
================================================================================

These patterns are worth following but the implementation should be custom.

--------------------------------------------------------------------------------
3.1 MCP Server (mcp_server.py)
--------------------------------------------------------------------------------
Pattern: Expose curated API subset as MCP tools via FastMCP.from_openapi().
  Token-based auth. Route mapping to filter exposed endpoints.
Why inspire: Hermes should expose its own session/run/artifact APIs as MCP
  tools, not presenton's presentation endpoints. But the pattern of loading
  an OpenAPI spec and filtering with RouteMap is worth following.
Hermes implementation: Use Hermes' own OpenAPI spec + FastMCP to expose
  session creation, run execution, artifact retrieval as MCP tools.

--------------------------------------------------------------------------------
3.2 mem0 OSS Memory (services/mem0_oss_memory.py + mem0_presentation_memory_service.py)
--------------------------------------------------------------------------------
Pattern: Semantic memory using mem0 (Qdrant + fastembed + spaCy). Scoped by
  presentation_id and conversation_id. Graceful degradation.
Why inspire: The concept of scoped semantic memory for presentations is
  valuable, but mem0 adds heavy dependencies (Qdrant, spaCy, ONNX models).
  Hermes should implement semantic memory using its own infrastructure.
Hermes implementation: Use Hermes' existing memory system or InsForge's
  vector search capabilities. Implement scoped retrieval by session_id
  and run_id instead of presentation_id.

--------------------------------------------------------------------------------
3.3 Document Ingestion Pipeline (LiteParse + DocumentsLoader)
--------------------------------------------------------------------------------
Pattern: Multi-format document ingestion with OCR. Node.js subprocess for
  high-quality parsing. Dispatch by extension.
Why inspire: The dispatch pattern and format coverage is excellent, but
  the Node.js LiteParse dependency is heavy. Hermes should use Python-native
  parsers where possible.
Hermes implementation:
  - PDF: pymupdf or pdfplumber (already available)
  - Office: office_document_service.py (Tier 1 — directly reusable)
  - Images: Pillow + pytesseract or Hermes OCR tools
  - Avoid the Node.js LiteParse dependency entirely

--------------------------------------------------------------------------------
3.4 Presentation Data Model (models/sql/presentation.py + models/sql/slide.py)
--------------------------------------------------------------------------------
Pattern: Presentation -> Slides with content (JSON) + ui (hydrated components).
  Version field for v1/v2 template systems. Outlines, structure, layout stored
  as JSON columns.
Why inspire: The data model is presenton-specific. Hermes should model this
  as Session -> Runs -> Artifacts, where each artifact is a slide deck.
Hermes implementation:
  - Session (replaces Presentation) -> has Runs (generation attempts)
  - Run -> produces Artifacts (slides, exports, images)
  - Use InsForge tables: sessions, runs, artifacts, slides
  - Store slide content as JSONB in Postgres (InsForge)

--------------------------------------------------------------------------------
3.5 Concurrent Service (services/concurrent_service.py)
--------------------------------------------------------------------------------
Pattern: Simple asyncio task tracking with done callbacks.
Why inspire: Too simple for production. Hermes should use a proper task queue
  (Celery, RQ, or InsForge Edge Functions) for background generation.
Hermes implementation: Use InsForge Edge Functions or Hermes background
  tasks for async presentation generation.

--------------------------------------------------------------------------------
3.6 User Config System (utils/user_config.py + utils/user_config_store.py)
--------------------------------------------------------------------------------
Pattern: Flat JSON file (userConfig.json) with all provider keys. Atomic writes
  with backup + lock. Env var mirroring.
Why inspire: Single-user, single-file config. Hermes should use InsForge
  secrets management or a proper config service.
Hermes implementation: Use InsForge secrets for API keys. Use InsForge
  database for user preferences. No flat-file config.

--------------------------------------------------------------------------------
3.7 PPTX Font Replacement (templates/pptx_font_utils.py)
--------------------------------------------------------------------------------
Pattern: Direct PPTX XML manipulation via zipfile + ElementTree. Theme font
  resolution (+mn-lt, +mj-lt). Embedded EOT extraction. Fontconfig aliases.
Why inspire: The XML manipulation approach is clever but tightly coupled to
  the PPTX format. If Hermes supports PPTX import, this is the reference.
  If not, skip entirely.
Hermes implementation: Only if PPTX import is required. Otherwise, use
  the bundled convert binary's font handling.
